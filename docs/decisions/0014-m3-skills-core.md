## 共通入力と行動規則

### Commandと同時刻の順位

```ts
// 既存の at / seq / player を持つCommandの分岐を1つ追加する。
{ kind: 'skill'; slot: 1 | 2 }
```

slotは表示どおり1始まりである。skill1は1、skill2は2へ変換し、配列アクセスだけslot−1を使う。物理キーE/R、SkillId、効果量、発動先座標、成功フラグを送らない。simが本人の枠から効果を決める。押下エッジ1回で1入力、主副のOR・repeat除外・blur等での解除は0013を使う。M3-3では押し離しCommand、設置プレビュー状態、汎用ターゲット引数を先に作らない。設置型の離して確定する入力はM3-4で追加する。

同時刻はmove／keys／yaw → Q → 各人の行動 → リリース／接触である。行動順位は次とする。

**ステップ ＞ キャッチ ＞ 跳ね返し・投擲 ＞ スキル1 ＞ スキル2 ＞ フェイント ＞ 球召喚**

個人ごとに最初に成立した1行動だけを採用する。予約作成も1行動である。高順位が不成立なら低順位を試す。パッシブ押下は成立扱いにせず、下位を妨げない。スキル間は種類やキャラにかかわらず枠1が先で、配列順・seq・通信到着順では変わらない。同じ人・同じ時刻・同じslotの重複押下は最小seqの1件だけを評価する。時間の異なる新しい押下は別の試行である。

たとえばEと投球を同時に押すと投球だけが始まる。その投球へ予約を後付けしない。Eで予約し、後の時刻に投球する必要がある。EとRが同時に成立可能なら予約だけを作り、移動しない。枠1がCT中・パッシブ・未実装などで不成立なら枠2を試す。

### 発動可否

保持／非保持のどちらでも、下表と各スキルの条件を満たせば発動できる。行動入力の先行予約は作らず、不成立の押下を硬直終了後に実行しない。「予約」は次球強化の状態だけを指す。

| 発動時の状態 | オーバーチャージ予約 | ブリンク |
|---|---|---|
| play・dangerあり・生存・actionなし | 可 | 可 |
| windup中。リリースと同じ時刻も含む | 不可 | 不可 |
| 投球後／返球後recovery、catch-recovery | 不可 | 不可 |
| catch／parryの発生・受付中 | 不可 | 不可 |
| catch-whiff | 不可 | 成立すれば残り硬直をキャンセル |
| parry-whiff | 不可 | 不可 |
| step／hitstun中 | 不可 | 不可 |
| feint開始時刻より後の新しい押下 | 成立すればフリをキャンセル | 成立すればフリをキャンセル |
| KO、result、over、初球の操作開始前 | 不可 | 不可 |
| 爆発後、新しい危険時計が始まるまで | 不可 | 不可 |
| 通信中断・メニュー等の入力抑止中 | 新しい押下を送らない | 新しい押下を送らない |

rules.mdが救済する空振りはキャッチ空振りである。跳ね返し空振りへ救済を広げず、ブリンクだけを「即時移動系」とする。硬直終了ちょうどでは終了処理後に新しい入力を受け付ける。ただしwindupは同時刻の照準を待ってリリースするため、その時刻のskillも不可である。フリとスキルが同時入力なら上記順位を使い、同じ時刻に二つの行動を成立させない。

コスト・CT・到着先の検査が済むまで、スキル側はactionを消さない。現在の`applyCommand`にあるフリの先行解除を、そのままskillへ適用してはならない。不成立のブリンクで空振りやフリだけを消す抜け道を作らない。パッシブ押下はフリ・予約・球・資源・CTを含むstateもeventsも変えない。

爆発後の歩行・通常ステップ可という既存規則は維持する。ブリンクを通常ステップと同じ停止中の例外にはしない。CTはplay中の絶対時刻で進み、被弾硬直・KO・爆発待機でも回復する。result／overでは使用不可表示にし、次ラウンドで初期化するため残秒の回復表示を行わない。通信中断はsim時刻自体を止める。Escはオンラインsimを止めないため、CTと予約期限は進む。

## 最小の状態と定義の境界

```ts
// SkillIdをgame/characters.tsからsim/types.tsへ移す。既存8IDにeconomyを追加する。
type SkillSlot = 1 | 2;
// Participant、PlayerStateの両方へ必須追加する。
skills: readonly [SkillId, SkillId];
// PlayerStateの可変状態へ必須追加する。
skillReadyAt: [number, number];
overcharge: { slot: SkillSlot; expiresAt: number } | null;
```

SkillIdは`overcharge`・`blink`・`phantom`・`boost-ring`・`chain`・`charge`・`trap`・`energy-bolt`・`economy`とする。型の旧定義や互換用の再exportは残さず、利用側のtype importを揃える。`charge`は既存の蓄勢、`economy`は省エネである。

`rosterMatch`がCHARACTERSからstatsとskillsを複製し、`createInitialState`へ渡す。simはgame層のキャラ表をimportせず、PlayerStateのskillsだけで発動・パッシブを判断する。Participantに2IDを足す方が、simへcharacterIdと全キャラ表を持ち込む案や、stepへ別のロスターを毎回渡す案より小さい。完全stateだけで予約中の保存復元ができ、テスト専用の組合せもsimを変えずに作れる。名前・配色・未実装の説明文はgame層のままである。

初期化ではskillsがちょうど2件の既知IDであることを検査する。空枠・欠損・未知IDを補完しない。同じIDの2枠も受理するが、パッシブは`includes`で一度だけ効き、オーバーチャージ予約は人物あたり1件で重ならない。CTは使用したslotに属する。正式4択の構成は変更しない。

初期値は`skillReadyAt = [0, 0]`、`overcharge = null`。CTは`now >= skillReadyAt[slot - 1]`で使用可能とする。期限到達時に0へ書き換える処理や、残秒の積算は不要である。パッシブ・未実装枠のreadyAtは0を維持する。時刻は既存の安全な非負整数単位であり、1秒＝60,000である。

数値は`SimConfig`へ`overchargeCost = 6`、`overchargeCooldown = 8秒`、`overchargeDuration = 8秒`、`overchargeSpeedMultiplier = 1.10`、`overchargePowerMultiplier = 1.25`、`blinkCost = 6`、`blinkCooldown = 9秒`、`blinkDistance = 4`、`chargeGoodReward = 3`、`economySummonCost = 3`を追加する初期案である。コスト6は画面の1.5、3は0.75に相当する。効果別の少数の分岐で十分で、関数を定義表に埋め込む効果言語・効果配列・フック登録は作らない。表示に必要な種別・実装状態は小さい共有判定から導き、sim判定とHUDで別の有効ID一覧を保守しない。

## 01 オーバーチャージ

### 予約・支払い・終了

| 場面 | 結果 |
|---|---|
| 有効枠の押下。行動可、CT終了、予約なし、現在コスト1.5以上 | `overcharge = { slot, expiresAt: now + 8秒 }`。支払い0、CT開始なし |
| 予約中の再押下。別slotに同じ効果がある場合も含む | 不成立。期限の延長・交換・解除・追加消費なし |
| 予約成立後にフリ・召喚・ブリンクを使用 | 通常どおり支払い可能。予約分の資源を取り置きしない |
| 期限前に手投げが実際にリリースし、現在コスト1.5以上 | 1.5を支払い、予約を消し、予約元slotのreadyAtをリリース時刻＋8秒にする。今回の球だけ強化 |
| リリース時にコスト不足 | 通常球を投げ、予約を消す。スキル分の支払い・CTは0。「強化なし：コスト不足」を通知する |
| 投球が正面条件等で不成立、または被弾でwindup中断 | 手投げ未成立なので支払い・CTなし。予約は期限まで残す。KOなら下記どおり消す |
| 8秒の期限ちょうど | 入力・リリースより先に予約を消す。支払い・CT・返金なし。ちょうどの手投げは通常球 |
| 本人が跳ね返しに成功 | 本人の未使用予約を消す。支払い・CTなし。返球には使わない |
| キャッチ成功／拾う／召喚、非KO被弾、他人の返球 | 本人の未使用予約を維持。8秒は延長しない |
| 爆発後も本人が生存 | 未使用予約は期限まで維持。待機中も期限とCTは進む。新規発動は不可 |
| 本人KO、ラウンド終了 | 未使用予約を消す。既に支払ったコスト・CTを返さない |
| 次ラウンド・引き分け再試合・新試合 | 全員のCTを0、予約をnullへ初期化。skillsは同じ構成を維持 |

予約時にも必要コストを検査するが、支払いはしない。資源不足で有効にできない予約を先に点灯させないためである。予約後の資源使用は制限せず、リリース時に再検査する。強化の不成立を理由に通常投球まで止めない。不足時に予約を消すのは「次の手投げ1球」を終えたためであり、追加の違約コストやCTではない。手投げが発生しなかった場合と区別する。

予約の有効区間は`[予約時刻, expiresAt)`。次事象へ予約期限を追加し、入力のない区間でも期限ちょうどで消す。CTは比較だけなので次事象を追加しない。期限がtick終了と重なる場合も失効を先に反映し、次tickで同時刻の新入力を処理する。復元直後の期限切れも入力前に除去し、過去の期限を次事象に選んで時刻を逆行させない。

### 球へ適用する値

通常の4球種とADSの非追尾手投げへ適用する。強化はリリースで確定し、風切り・中央通過・顔の段階変化で再計算しない。初期案の計算順は以下である。

- 速度：基本球速 × 攻撃倍率 × 危険倍率 ×（1＋ラリー加算）× 1.10。その後に当該球種の総上限1.60倍、既存の最低飛翔時間と球速下限を適用する。
- 威力：基本ダメージ × 危険倍率 ×（1＋ラリー加算）× 1.25。その後に総上限2.50倍を適用する。攻撃値をダメージへ新たに掛けない。

制限済みの速度へ後から1.10を掛けてはならない。現在の`launchBall`が行う飛翔時間制限の入力側へ強化を渡す。手投げは従来どおりラリー加算0で開始する。対象なしの狙い投げに対象距離を捏造せず、現行の非追尾投球の制限を使う。近距離の球速下限が飛翔時間より優先する既存例外も維持する。

BallAttackには確定後のspeed・damageが既にある。今回、バフ配列や元倍率の保存フィールドは追加しない。跳ね返し成功時は返す人の能力・危険倍率・今回までのラリー加算だけで新しい球を作り、強化引数を渡さない。入射球の倍率を返球へ引き継がない。追尾解除だけではspeed・damageを落とさない。キャッチ・被弾・攻撃消失・爆発でその飛行が終わる。

### 相手に分かる予約

`overcharge !== null && now < expiresAt`を唯一の予約表示の根拠とする。本人のHUDには「予約：残り秒／次の手投げで1.5消費」を出す。腕に細い発光帯、名札に「強化予約」を表示し、本人が保持中なら球の外側へ細い輪を付ける。非保持なら他人の球を光らせず、腕と名札だけを表示する。素材の骨格名へsimを依存させない。

球種色・顔・チーム色を塗り替えない。輪の内径は0012の球保護規則を守り、flash=0でも予約文字と輪郭を残す。リリース後は予約表示を消す。強化済み飛行専用の常時発光やSEは本スライスでは追加しない。後から飛行の速度だけで強化の有無を推測しない。

## 08 ブリンク

入力時刻の最新の論理yawから、`to = { x: x - sin(yaw) × 4, y, z: z - cos(yaw) × 4 }`を求める。移動キー、陣の前後方向、表示カメラの揺れ、pitchは使わない。到着先だけでなく移動も水平で、yaw・HP・ステップ資源・危険時計・球の所有者を変更しない。ブリンク自体の発生待ち・回復硬直は追加せず、成立後はactionなしとなる。同時刻の他行動は共通の1行動規則で禁止する。

### 合法位置

キャラ中心の既存範囲、x＝±playerHalfWidth、a陣z＝[playerMinDepth, playerMaxDepth]、b陣z＝[−playerMaxDepth, −playerMinDepth]を使う。境界を含み、4m先が範囲内なら成立する。範囲外なら不成立とし、位置・コスト・CT・action・追尾を変えない。壁まで短縮した移動や成分別クランプは行わない。これにより「4m」の意味とプレビューが一致し、斜めの壁滑り判定を増やさずに済む。

M3-3の各陣の移動範囲は凸な長方形であり、合法な始点と終点を結ぶ線分は金網・中央フェンスを越えない。味方との重なりやケージ内小物を新しい不成立条件にしない。白線内に限定せず、キャラの金網内範囲を使う。封鎖エリアはまだ存在しない。M3-5で封鎖を実装する時に、その境界を通過しない検査を同じ到着計算へ足す。今回、任意障害物の探索や衝突基盤を作らない。

成立する時だけpositionを一度にtoへ変え、コスト1.5を引き、使用slotのreadyAtをnow＋9秒にする。保持中の球はheldのまま同じownerについて来る。中央を越えないため中央通過イベントも危険時計の更新もない。着地地点のloose回収は既存の絶対60Hz境界だけで行い、移動線分上の球を拾わない。

### 追尾解除と同時接触

発動直前に非保持で、現在のflightが自分をtargetとするhoming球なら、球種・向きによらずhomingだけをfalseにする。target・speed・damage・現在の速度は維持し、以後はその速度で直進する。ステップの球種別有効方向は変更しない。解除する操作は同じでも、ステップは方向相性あり、ブリンクは方向相性なしである。味方宛ての球や既に非追尾の球へは何もしない。

同時刻に新しくリリースされる球は入力処理後に生まれるため、ブリンクで将来の追尾を予約解除しない。既存球なら`now > releasedAt`の条件もステップと揃える。保持中は追尾解除を行わない。無敵・防御受付・直撃対象の変更は一切追加しない。

瞬間移動の経路には掃引接触を作らない。ブリンク成立者については、移動前に計算したその時刻の接触候補と`pendingContacts`の当人分を破棄し、到着位置で接触候補を作り直す。他人の候補、特に切り上げ前に成立して保存した接線接触は残す。到着先で球と重なれば同じ時刻に被弾し得る。前後1時刻単位も検証し、「旧位置での誤被弾」と「到着直後だけ無敵」の双方を防ぐ。解除後の床・外周での攻撃消失も同時刻の接触解決後に再評価する。

### 本人へのプレビュー

ブリンクを持つ生存者には到着予定地点の小さい床印を常時出す。押し続けてプレビューする別操作は作らない。同じ純粋な到着計算をsimと表示から呼び、表示では入力予定の論理yawを使う。範囲外なら4m先の予定印と「範囲外」を出し、合法な位置へ動けるように見せない。CT・コスト・硬直による不可も枠内の文字で示す。メニュー・中断・KO・結果中は印を隠す。

プレビューは現在の候補であり、通信先へ座標を送らない。発動時の状態でsimが再検査する。位置の瞬間変化は予測表示へ即時反映し、4mの線形補間で途中を歩いたように見せない。新しいsim状態を加えず、隣接表示状態の通常移動では生じない変位を表示側で補間しない方法を使う。補間の可否が判定へ影響してはならない。論理yaw/pitchを勝手に回転しない。

## パッシブと検証用PP

蓄勢は`skills.includes('charge')`の時、goodキャッチ報酬だけを内部2から3へ置き換える。so-soは1、justは4、justの最大HP3%回復、parry報酬1は変更しない。上限20へ従来どおり切り詰め、同じ効果が2枠にあっても加算を重ねない。

省エネは`skills.includes('economy')`の時、召喚の必要コストと支払いを内部4から3へ置き換える。既存の自陣loose・danger・行動なしの成立条件と時計継続は維持する。失敗時は0消費。他の支出は安くしない。パッシブにCT・予約・発動イベントを設けない。押下したslotがパッシブなら無条件に何もせず、HUDにE/Rを促さない。

PPキャラは**テスト内の定義だけ**に置く。5/5/5、2枠`['charge', 'economy']`のfixtureをParticipantへ変換して使い、表示試験は同じスキルの表示関数へ渡す。AAはVOLT、APはANCHOR（本段階のchainは未実装）と、テスト内の`['blink', 'charge']`でも確認する。能力・2枠の解決経路を共有し、キャラIDによるsim分岐を作らない。

正式CHARACTERS、CharacterId、部屋の許可ID、開始画面の4択は増やさない。隠しURL・開発メニュー・永続化・通信上のPP選択も作らない。0012のPP試遊は本段階では自動検証までとし、人間のPP試遊は未検証に残す。試遊が必要になった時に選択経路を別途決める。試験が通ったことを正式採用としない。

## HUDと確定イベント

各枠は設定から現在の主副キーを引く。実装済みアクティブには必要コスト、使用可／CT残秒、予約の残秒、不成立条件を文字で出す。CTと予約は別の値である。`max(0, readyAt − now)`または`max(0, expiresAt − now)`から導き、正の残時間が0秒表示にならないよう0.1秒単位で切り上げる初期案とする。パッシブは「常時：蓄勢 good +0.75」「常時：省エネ 召喚0.75」、未実装枠は従来どおり「未実装」とする。

理由は小さい純粋関数でsimの成立検査と共有する。評価順はパッシブの無処理 → 未実装 → 試合状態／待機 → KO → action制限 → CT → 予約済み → コスト不足 → 到着先不正とする。優先行動が成立して試行されなかったアクティブには「同時入力の優先行動」を返す。予約済み表示では再押下不可と、現在コスト不足なら「次の手投げは強化不可」も併記する。予約を持っているだけで常時コスト不足の短文をイベントとして流さない。

継続表示のCT・予約・腕／球の輪は描画中のsim状態から導き、オンラインでは予測表示として確定stateへの訂正を受け入れる。成功音・成功文字はそこから発火しない。予約作成・失効・パッシブ報酬・CT終了・ブリンク成功の専用イベントは不要である。

押下した時の理由を後のstateから推測しないため、追加するSimEventは次の1種だけとする。

```ts
{ kind: 'skill-rejected'; at: number; player: PlayerId; slot: SkillSlot;
  reason: 'unimplemented' | 'phase' | 'ko' | 'busy' | 'cooldown'
    | 'reserved' | 'cost' | 'destination' | 'priority' }
```

失敗した押下試行に1件。パッシブ押下は0件。予約を使う手投げの資源再検査で不足した時も、予約元slotの`cost`を1件出す。押下とリリースが同時なら別の試行として記録し、枠の短文は後のリリース結果で置き換える。期限切れ・KO等の自動消去には出さない。終了済みoverは既存どおりsim処理を終えており、新イベントを作らず常設HUDで使用不可を示す。reasonは機械的な理由だけで、説明文や表示msをsimへ保存しない。通信上の拒否ACK（late／identity等）は別の失敗であり、このイベントを捏造しない。

M3-1の確定列→`updatePresentation`→HUDへ通し、本人のスキル枠の短文だけを初期案1秒間表示する。予測・ホスト再実行から直接通知しない。`skill-rejected`も短命通知として、300ms超の遅着・非表示・中断・再同期履歴・旧ラウンドでは省略し、消費位置は進める。SE・VFX・ヒットストップは要求しない。勝敗・被弾の共通メッセージを置き換えない。不成立はstateを変えずイベントだけを増やせるので、「無消費」と「events完全不変」を混同しない。

## 保存復元・ホスト再実行・受信検査

skills、skillReadyAt、overchargeは完全stateに含める。BallAttackの確定値も既存どおり保存する。CTと予約を端末のsetTimeout・localStorage・Bot記憶へ分けない。通信中断の確定復元点へ戻し、新epochの同期でそのまま再開する。停止していた実時間を期限へ加算しない。再接続・完全復元と次ラウンドの初期化を混同しない。

100ms内の遅着skillも通常入力と同じ順でホストが再実行する。予約・支払い・移動・解除・失効・不成立イベントまで、同一state・config・Command列から一致させる。入力の再送は既存player／seqで重複排除し、再実行のたびに外部へ支払い・音を送らない。ホストも確定列で提示する。各人の処理は既存のPlayerId昇順で、全員分の行動後にリリースと接触を解決する。

| 境界 | 必要な変更 |
|---|---|
| `validCommand` | kind=skillはslotが数値1または2だけ。既存at／seqの整数検査、本人ID検査を維持し、全Commandのplayerを既知PlayerIdとして検査する。skillId・座標等の余分なキーを拒否する |
| `validMessage`のstate | skillsが既知ID2件、skillReadyAtが安全な非負整数2件、overchargeがnullまたは正しいslot・期限のオブジェクトであることを必須検査。予約元skillsがoverchargeで、同slotのCTは終了済みであることも検査する |

`validMessage`単独にはsessionがないため、構文検査とロスター一致検査は分ける。後者は0013のC12-4cで未実施と記録された部分も合わせて閉じる。受信skillから任意の効果IDを申告できなくても、改変snapshotのskillsを信じれば境界が崩れるためである。不一致は既存の不整合停止へ進め、黙ってVOLTや初期stateへ戻さない。部屋にskillsを二重申告する項目は増やさない。旧保存部屋は既存の版不一致扱いとし、移行・削除を行わない。

## Botと実装の分割

M3-3ではBotからアクティブskillを出さない。回収・投球・フリ・カバーの既存思考を維持する。パッシブは本人のskillsによるsim効果なのでBotにも自動適用される。Bot専用のCTや優先判断は追加しない。アクティブを使った再現はテストのCommand列で行い、スキルを使わないBotとの試合だけで対戦バランスを評価しない。

実装は、型・参加構成・入力／受信形式 → 共通ゲートと予約・強化球 → ブリンクと同時接触 → パッシブ → HUD・確定通知と統合、の小単位で進める。各単位で資料の受け入れをテストへ写し、未実装の挙動によるRedを確認してから最小実装する。既存fixtureはskills等の必須項目を明示する新形式へ揃え、無スキルの旧形式を通す補完を追加しない。
